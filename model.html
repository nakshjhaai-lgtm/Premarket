The models

What it is, how it was trained, how it is validated, and where it fails.

Origin

The forecaster is a faithful implementation of the 3 layer LSTM stock model from the DataCamp tutorial “LSTM Stock Prediction with TensorFlow in Python” (Jaa_smb, September 2019). The tutorial's training code was rebuilt and executed on the exact stack it specifies, Python 3.6 and TensorFlow 1.6, because the model uses tf.contrib.rnn, which does not exist in TensorFlow 2.x. The training environment was compiled from source (OpenSSL 1.1.1w, libffi 3.3, CPython 3.6.15) in this project's sandbox.

Architecture

Inputmid price = (High + Low) / 2, MinMax scaled per 2,500 row window; last fitted window frozen for inference
Cells3 stacked tf.contrib.rnn.LSTMCell layers: 200 → 200 → 150 units, Xavier initialized kernels, zero initialized biases, forget bias 1.0 added at run time (TF 1.6 semantics)
Trainingtruncated BPTT, 50 unrollings, batch 500, Adam 1e-4 with staircase decay (×0.5), gradient clipping 5.0, dropout 0.8 (train only), 30 epochs, mid epoch validation MSE on the test split
Output headdense 150 → 1, trained on one session ahead scaled mid prices
InferenceJS port of the LSTMCell math; warm start with 49 real observations, predict session t+1, then feed predictions back for a 5 session path (same protocol as the article)
Footprint~693k float32 parameters, shipped as a base64 blob (~2.8 MB) and decoded once per cold start; a full 10 step forecast takes 1 to 2 seconds in Node

Training data

  • NIFTY 50 (^NSEI): 4,682 daily bars, 17 Sep 2007 to 16 Oct 2026, fetched from the Yahoo Finance chart API. Train/test split at row 4,382, leaving the most recent 300 sessions as a never trained on test region.
  • Scaler window: the frozen MinMax scaler covers roughly Aug 2017 → mid 2025, so current index levels sit inside the trained range (a runtime guard flags forecasts if prices ever drift outside it).

Validation against the article

The same training script was first run on the article's own dataset, HPQ daily bars 1970 to 2017 (12,076 rows, split 11,000, exactly as published). The result: test MSE 0.00245 at epoch 30, best 0.00231, against the article's reported range of roughly 0.0023 to 0.0025. The dashboard's article exhibit panel renders the TF session's own final epoch predictions for that run, exported directly from TensorFlow, not recomputed in JavaScript.

The JavaScript inference engine is validated separately: for each exported model it must reproduce TensorFlow's 10 step sampling output for the article's warm start windows within 5×10⁻³ (float64 JS vs float32 TF). The validation harness ships with the project (tools/validate-lstm.mjs).

Live backtest protocol

Every daily run computes a rolling backtest over the most recent 10 sessions: for each day the model is warm started on the 49 real observations ending two days prior, predicts one session ahead, and the error and direction hit are recorded. These numbers appear on the dashboard next to the forecast, so the model is judged continuously rather than once.

Limitations, read before trusting anything

  • Multi step paths widen in error quickly. The one session ahead number is the meaningful one; sessions 3 to 5 are directional context only.
  • The model sees only price history (mid prices). It is blind to news, RBI policy, elections and overnight gaps. That is exactly why the four rule based checks, the context panel, and since October 2026 the daily news and earnings layer (headlines, earnings dates and event flags on the dashboard and stocks page) exist alongside it: the world is shown to you, not silently blended into the numbers.
  • Weights are frozen at training time. If NIFTY drifts far outside the scaler range the site flags the forecast as unreliable; the fix is retraining, which is a documented, repeatable procedure in this project.
  • A backtest on 10 sessions is small sample. It is evidence of sanity, not of edge.
Not investment advice. This model is research tooling published with full provenance so its claims can be checked. Do not trade on it alone.

Second model: Google TimesFM (offline)

Alongside the LSTM, the project runs TimesFM 2.5 (200M parameters), Google Research's open source time series foundation model, pretrained on roughly 100 billion time points, as a zero shot second opinion on the same NIFTY series. TimesFM never trains on our data; it forecasts directly from context, which makes it an independent reference: when two very different architectures agree, the forecast carries more weight; when they disagree, that disagreement is itself information.

  • Checkpoint: google/timesfm-2.5-200m-pytorch via the timesfm PyPI package.
  • Protocol: last 1,024 daily closes as context, input normalization on, positivity inference on; a 5 session forward path and a rolling one session ahead backtest over the same window the LSTM is scored on.
  • Runs offline (the ~800 MB checkpoint does not fit a serverless function); results are published as a static artifact and stamped with their as of date. The dashboard flags the analysis once it goes stale.
  • Refresh procedure is documented in the project README (one venv, one script).
Why two models? The LSTM is the article's architecture running live in the scan; TimesFM is a foundation model cross check. Neither is assumed correct; the dashboard shows both backtests so you can weigh them yourself.

Third layer: the adaptive ensemble (primary forecast)

The forecast the dashboard leads with is neither model alone. It is a learned blend:

ensemble(t+1) = w · TimesFM(t+1) + (1−w) · (LSTM(t+1) − bias)

The weight w and the LSTM's bias correction are not chosen by hand. They are found by grid search offline over a 250 session (~1 year) walk forward window in which both models predicted every session one step ahead using only the data that existed beforehand, with no leakage. The parameters that would have minimised RMSE over that year are the ones shipped. On the current window TimesFM dominates, so w lands near 1; the second half of the window leans slightly more on the LSTM than the first half, which is exactly the drift the weight is relearned to track.

And it keeps learning after deployment. Every 09:00 IST scan records its prediction in a model scorecard (Netlify blobs). When the session prints, the entry is scored against the actual close. Once five sessions have resolved, the live w and bias are relearned from the most recent 30 resolved sessions and used for the next morning's blend. the offline parameters remain the fallback. The dashboard shows both the provenance of the current weight and the recent scorecard rows with each model's error.

  • Freshness guard: the TimesFM component is only blended while its artifact is ≤5 sessions old; otherwise the report honestly falls back to the bias corrected LSTM and says so on the dashboard.
  • Everything is reported with measured walk forward numbers: no in sample flattery, no fabricated accuracy.

Per stock forecasts (US, global, India ADRs)

The Stocks page applies the same TimesFM checkpoint, zero shot, to ~50 major symbols: US mega caps and sector leaders, SPY/QQQ/DIA benchmark ETFs, global ADRs and Indian ADRs (listed on the NYSE, USD). Each symbol gets a 5 session forward path plus a 10 session one session ahead backtest (direction hit and % RMSE) computed in one batched offline run; the page is searchable and sortable, and every row carries its own as of date. The refresh procedure lives in the README alongside the NIFTY one.

Provenance of the shipped artifact

  • Training script: the tutorial's pipeline, parameterized only where pandas 1.1.5 / numpy 1.19 required it (.as_matrix() → .values), with an export epilogue added. Deviations documented in the project.
  • Exported artifacts: all trainable variables (multi_rnn_cell/lstm_cell*/kernel|bias, w, b), the frozen scaler min/max, final EMA state, TF reference predictions, and per epoch test MSE.
  • Packed for the web as float32 little endian base64 (tools/pack_model.py), decoded by lib/lstm.mjs.
